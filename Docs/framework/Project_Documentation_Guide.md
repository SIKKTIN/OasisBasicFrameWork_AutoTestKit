# Oasis 项目文档规范

本规范由 OasisBasicFrameWork_AutoTestKit（TestHelper）仓库维护，供采用本框架的 UGC 工程及工具仓库自身使用。规范随仓库分发，不依赖其他文档 Skill 或个人电脑上的安装路径。

本文规定文档放在哪里、各自负责什么，以及开发过程中如何维护。它不改变代码、配置、蓝图或资源的目录契约；这些仍遵循框架架构、Package 规范与目标项目约定。项目上下文初始化、框架部署和可选包增装 Skill 均引用本规范，实际目标工程的文档和运行结果仍需在各次执行中核实。

## 1. 区分工具仓库与目标项目

| 对象 | 保存内容 | 默认入口 |
| --- | --- | --- |
| TestHelper 工具仓库 | 通用架构、Package 与数据契约、工具和部署指导、模板说明、框架开发记录 | 根 `README.md`、`Docs/framework/README.md`、`Docs/dev/目录.md` |
| 目标 UGC 工程 | 本项目的设计、具体玩法内容、实际接入情况、业务开发与验收记录 | 项目 `README.md`（如有）、`Docs/目录.md`、`Docs/dev/目录.md` |

下文未特别标明的路径均相对于本次目标项目根目录。不能因为 Skill 位于工具仓库，就把目标项目的设计和进度写入工具仓库；也不能把模板说明当成目标已经部署或验证的证据。

框架本身的开发事项记录在 TestHelper 的 `Docs/dev/`；业务工程的接入事项记录在该工程自己的文档目录。通用能力与目标适配分开记录并互相引用，避免在两处重复维护同一份设计或实施正文。

## 2. 目标项目的默认路径

```text
项目根目录/
├── README.md                    # 如有：项目简介及文档入口
└── Docs/
    ├── 目录.md                  # 全局文档导航与实际路径约定
    ├── design/                  # 项目设计、规则、机制与流程
    ├── content/                 # 具体任务、物品、敌人、关卡等内容
    ├── dev/
    │   ├── 目录.md              # 开发事项、类别、状态与链接
    │   └── 按领域组织的事项文档.md
    └── concepts/                # 概念图、草图和方案参考
```

- 新项目默认使用 `Docs`，中文文件名和 Markdown 格式。分类目录与子目录按实际内容创建，不预先生成整套空目录和空文档。
- 已有项目使用 `docs`、`Docs/module`、`Docs/plan` 或其他等价路径时，保留现有名称。不要创建大小写不同的第二套文档根目录；链接使用磁盘上的实际大小写。
- 在项目 README 或既有文档入口中声明文档根目录和导航路径。缺少导航时，在已授权的文档建立或整理范围内补充 `Docs/目录.md`，列出已有路径及职责，不为套结构批量搬迁文件。
- 文档路径从目标项目的约定与导航取得，不从工具 `setting.json` 的旧项目路径或 MCP 当前打开的其他工程推断。
- 缺少设计或进度记录时明确报告缺失。只读初始化不自动创建文档，也不把包内 README 当作完整的项目设计或进度。

### 全局目录负责什么

`Docs/目录.md` 至少说明文档根目录、各分类的实际位置与用途、建议阅读顺序、开发进度入口，以及通用框架资料的查阅方式。链接应能从当前项目或已定位的工具仓库找到，不硬编码维护者个人的用户目录或盘符。

按“项目总览与规则 → 相关系统设计 → 具体内容 → 本次开发记录 → 关联实现与验证证据”组织阅读。分类内资料多时再增加分类索引；全局目录链接分类入口，不在每一层重复维护所有文件清单。

已有等价导航直接复用。TestHelper 当前使用根 README 与 `Docs/framework/README.md` 作为通用文档入口，本规范不要求再建立重复的全局目录。

## 3. 设计文档：长期规则与机制

`Docs/design/` 回答项目为什么做、主要玩法如何运作，以及系统遵循什么规则。按项目需要组织项目总览、全局规则、玩法流程、系统机制和视听交互要求，不要求每个主题各建一份文件。

系统设计应说明：目标与范围、参与对象和状态、进入及退出条件、主要流程、失败与恢复行为、玩家可见反馈、与其他系统的关系。涉及联机、数据或配置时，还应明确：

- 哪些行为由服务端决定，客户端负责哪些请求和表现。
- 哪些状态仅在本局存在，哪些需要存档、复制或迁移，失败后如何处理。
- 哪些参数允许项目配置，实际配置来源在哪里。
- 对应的 Package 门面、配置、蓝图/UI 入口及所依赖的框架契约。

架构关系引用 [项目架构思想](Project_Architecture.md)、[Package 规范](Package_Structure.md)、[Meta 契约](Package_Meta.md) 与 [数据指导](DataCore_Guide.md)，目标文档主要说明自己的规则和适配差异，不复制整份通用说明。

设计中明确区分已实现规则、已确定但待实施的规则与待讨论方案。实际实现不符时记录差异，不能仅因代码存在就把缺陷改写成设计，也不能仅凭设计文档声称功能已实现。

## 4. 内容文档：具体对象与实例

`Docs/content/` 回答某个对象是什么、有什么作用、在什么条件下出现或使用。例如一组任务、某类敌人、关卡、商品、物品或技能的具体设定。

- 通用任务状态机属于系统设计；某条任务的名称、条件、目标、奖励与关联角色属于任务内容。
- 内容已有稳定 ID 时记录 ID，并关联负责的系统设计、实际配置、资源和必要实现入口。文档目录不必与代码或配置逐层对应，也不要求每条配置各建一份文档。
- 实际生效数值注明权威配置来源，例如 Lua 配置、数据表或编辑器资产。数值变化时同步维护相关内容说明；不要另建一份无人同步的完整配置副本。
- 蓝图和 UMG 使用可定位的工程相对路径或已核实的资源路径；仅截图不能代替关键行为和配置来源说明。

## 5. 开发记录与项目进度

### 一件事项一份文档

新增功能、修复、优化、重构、框架初装和可选包增装，均在 `Docs/dev/` 按主要领域归类。计划、实施过程与结果放在同一份事项文档；接续工作更新原文档。跨领域事项选择一个主要归属，其他地方通过链接引用。

开始实施前写清目标与范围、关联设计或内容、涉及文件、实施步骤和验证方式。小事项可以用几段文字说明，不要求填满固定表格。概念探索可以先于开发计划；开始修改实现前仍应形成计划。

实施中同步记录范围调整、实际变更、问题与接续点；结束后补充验证结果和剩余事项。若只是开发记录遗漏或文档不一致，修正记录时依据可核实证据，不补造历史测试结果。

### 进度入口固定到开发目录

新项目使用 `Docs/dev/目录.md` 汇总进度。已有项目的等价事项索引可继续使用，并在全局目录中明确它就是进度入口。

最小索引示例（仅说明格式，不代表真实事项）：

```markdown
| 事项 | 类别 | 状态 | 文档 |
| --- | --- | --- | --- |
| 首次接入基础框架 | 框架接入 | 进行中 | 对应事项文档的相对链接 |
```

状态至少区分“计划中、进行中、已完成”。暂停或阻塞等状态按实际需要补充，并在事项正文写明原因与恢复条件。状态以实际实施和本次约定的验证范围为依据，不能仅凭日期较新、文件存在或计划打勾就判定完成。

代码已经修改但必需验收未完成时，应明确写“实现完成，待验收”，不能笼统列为全部完成。文档编写完成、等待用户审阅，也应区别于实施或产品验收。历史记录未复核时注明原记录状态，不能把它当成本次重新验证。

开发事项索引负责进度，具体文档负责细节。没有独立需要时，不再维护另一份重复的总进度正文；项目里程碑可在项目总览中引用事项索引。

### 事项文档的必要信息

| 信息 | 要回答的问题 |
| --- | --- |
| 目标与范围 | 解决什么问题、预期行为是什么、本次做到哪里 |
| 关联资料 | 依据哪些设计、内容、配置和已采用的概念版本 |
| 涉及文件 | 哪些代码、配置、资产或文档将变化，分别负责什么 |
| 步骤与依赖 | 如何实施，依赖什么，哪些地方尚需确定 |
| 验证方式 | 如何判定符合预期，需要覆盖哪些关联行为 |
| 实际结果 | 修改了什么，验证了什么，哪些尚未完成或未验证 |

## 6. 绿洲框架接入与验证记录

部署事项除上述内容外，还需记录目标工程、基础框架与选包版本、实际选项、已有内容的保留/合并情况、实际绑定入口、变更资产及表行、生成范围、备份位置和恢复线索。来源模板和独立示例分别标明，不把模拟奖励或示例任务写成正式业务规则。

识别手写输入与生成产物：修改输入后按需生成，并记录实际生成结果；不要把手改生成文件描述为长期配置方式。包内 `README.md` 继续说明技术边界、接口、数据和生命周期；项目级设计和接入记录通过链接引用它，不把实施进度塞进所有包 README。

验证记录按实际覆盖区分：

| 验证类别 | 应记录的证据与边界 |
| --- | --- |
| 阅读与静态检查 | 核对的文件、声明、引用或格式；不能证明游戏能启动 |
| 隔离测试 | 实际命令、结果、使用的引擎或存档替身；不能代替实机 |
| 编辑器资产检查 | 实际工程、蓝图绑定、编译、保存和读回结果 |
| PIE 实机验证 | 本次会话标识、平台、client/DS 日志位置、实际行为与结果 |
| 发布环境验证 | 实际版本与场景；跨对局、断线恢复、真实奖励等分别说明是否覆盖 |

请求派发成功不等于执行成功；零套件不等于测试通过；框架就绪不等于业务和玩家数据全部就绪。同局存档读回与跨对局持久化分别记录。用户明确不测试时记录“按要求未测试”，不虚构通过，也不擅自运行。

验证产物与完整备份按项目约定保存，在文档中给出位置与必要摘要。只保留需要长期查阅的截图或证据，不把大量运行日志、缓存或备份拷入文档树。涉及机制和技术细节时参阅 [开发、测试与调试指导](Development_Test_Debug_Guide.md)。

## 7. 概念图与参考方案

`Docs/concepts/` 按事项保存概念图、草图和方案参考，使用清楚的版本名。设计及开发文档引用同一份资料，注明采用的版本、采用部分及后续调整；示例文字、数值和布局不自动成为正式规则。

概念资料与最终交付资产分别保存；实际 UI、模型、纹理等仍遵循目标工程的资源目录约定。没有概念设计需求时不创建概念文件夹或额外图稿。

## 8. 阅读、写入与 Skill 接入边界

- **项目上下文初始化**：先确认目标，读取项目约定和导航，再查本次相关设计、内容、开发记录与实现。资料缺失时报告缺失，只读请求不创建结构、不补写计划、不运行生成器或 PIE。
- **新建或整理文档**：在用户指定范围内建立必要的导航、说明和记录。已有资料先归类与链接；迁移、删除或重命名应有具体必要性和可核对的范围。
- **普通开发**：由 [oasis-document](../../.agents/skills/oasis-document/SKILL.md) 在 Oasis 功能开发、修复、优化和重构任务中提供主动维护入口，按现有授权形成或更新事项计划，实施时维护记录，完成后同步受影响的设计、内容和索引。不因维护文档而增加逐文件确认；与其他 Skill 已有记录接续，避免重复计划。主动选用不表示后台监听，也不保证每次请求都会被选中，需在实际开发中核对。
- **框架初装与可选包增装**：预检仍保持只读，报告包含文档现状和拟新增记录。取得具体部署方案的确认后，在写入阶段记录实施计划与接入结果。部署本身不能替项目编造尚未确定的玩法设计。

这些职责已接入 [项目上下文初始化](../../.agents/skills/oasis-project-init/SKILL.md)、[基础框架部署](../../.agents/skills/oasis-project-deploy/SKILL.md) 和 [可选包增装](../../.agents/skills/oasis-package-deploy/SKILL.md) 的执行步骤。规范是统一依据，Skill 保留各自的执行与授权边界；没有引入新的 Skill 安装前提。Skill 文件更新不等于目标文档已生成或目标部署已验收，实施与检查范围见 [本次接入记录](../dev/文档规范接入现有Skill.md)。

## 9. 维护与检查

一条长期规则在负责它的设计或内容文档中维护，其他文档引用；开发记录说明本次变化与结果。新增、移动、删除文档时同步修正目录和关联链接，后续设计或实现变化时同步更新对应说明。

每次结束相关工作时检查：

1. 从项目入口能否找到相关设计、内容和本次开发事项。
2. 文档路径是否使用真实目录，是否误写到工具仓库或其他工程。
3. 已实现、计划、探索、未验证内容是否清楚区分。
4. 实际配置、资源和实现入口是否可定位，是否与正文一致。
5. 事项状态是否与实际结果一致，未完成内容是否有接续点。
6. 验证命令、环境与证据是否真实，是否误用了历史报告。
7. 导航和链接是否有效，是否产生重复正文、空目录或无依据的设计。
