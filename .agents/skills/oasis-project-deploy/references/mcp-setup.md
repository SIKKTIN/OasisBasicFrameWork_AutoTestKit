# MCP 安装、配置与连接指导

在部署前检查 MCP；工具缺失、请求失败或需要安装配置时按本文定位。本文只准备编辑器访问环境，框架文件、资产与 PIE 仍按 SKILL.md 的预检和确认流程处理。

## 先区分服务与客户端

编辑器端 MCP 服务负责访问 UE 工程；Codex 等客户端负责加载连接配置并展示工具。添加客户端配置不会安装编辑器服务。工具仓库的 `setting.json` 配置 Lua 和工程路径，不用于注册 MCP 服务。

先记录用户实际使用的编辑器版本、目标 `.ugcproj`、客户端与运行位置，再核对有效的服务配置和工具。连接地址取自该服务的安装说明、启动日志或配置。客户端运行在 WSL、容器或远程机器时，`127.0.0.1` 指向客户端所在环境，不能直接假定它是编辑器所在机器。

## 状态判断与处理

| 状态 | 判断依据 | 下一步 |
| --- | --- | --- |
| 安装状态未确认 | 工具不可见，且尚无安装文件、版本或日志证据 | 检查已知安装位置与客户端配置；收集安装说明，不直接重装 |
| 服务未安装 | 按适配版本的安装说明检查，确认必需服务或插件文件缺失 | 取得安装来源，按下一节准备安装 |
| 客户端未配置或未加载 | 服务安装有证据，但有效配置缺失、禁用，或当前会话未加载工具 | 补充或启用对应条目，重新加载客户端并发现工具 |
| 服务未启动或地址错误 | 配置存在，请求被拒绝或不可达；结合服务日志判断 | 核对完整地址、启动方式及进程；超时本身不能证明未安装 |
| MCP 可达但编辑器未连接 | MCP 握手或工具枚举成功，`ctx:` 无有效工程或编辑器请求失败 | 按服务说明连接编辑器，打开目标工程并重试 |
| 工程不匹配 | `ctx:` 返回另一工程或挂载根 | 选择正确编辑器实例或服务连接，重读上下文；禁止写入错误工程 |
| 能力不完整 | 工程可读，但缺少必要工具或支持的资产 API | 核对服务版本、工具启用设置与兼容性；列出缺项 |
| 已就绪 | 实际请求成功，工程与挂载匹配，必需能力已核对 | 返回框架预检，展示报告后等待框架部署确认 |

配置可以与服务故障同时存在，报告应保留各项检查结果。连接失败若没有足够证据，报告具体错误及待查项，不强行归入“未安装”。

## 未安装：先核实安装来源

本工具仓库不附带编辑器 MCP 服务安装包，也没有已确认的服务下载地址和通用安装命令。不要把开发目录内的 `DevelopmentTools/PetsGo/Tools/EditorMCP.py` 当作安装器；它是本地 HTTP 调用脚本，不部署服务，也不保证适配其他版本。

1. 优先查用户提供的安装包、服务维护方文档，以及已安装服务的随包说明；缺少时明确询问“当前编辑器版本对应的 MCP 安装包或维护方安装文档在哪里？”。无需索取整个客户端配置或凭据。
2. 根据该版本的说明核实：发布来源与版本、兼容的编辑器版本、运行依赖、安装目标、启用方式、启动命令或菜单、传输类型与连接地址、是否必须重启编辑器。未确认的字段标为待确认。
3. 展示可执行的准备方案：实际包路径或来源链接、要新增或替换的文件、配置差异、备份位置、启动步骤及必要的重启动作。授权覆盖后按说明执行；保留无关配置和现有安装，不自行猜测插件目录或覆盖其他版本。
4. 插件型服务按其说明安装并启用，独立进程型服务按其说明启动；STDIO 是否由客户端拉起也以服务说明为准。不要把某一种部署方式设为所有版本的默认方式。
5. 只在安装方式确实要求时重启对应服务或编辑器。编辑器有未保存内容时先处理保存状态；需要用户手动操作时说明具体步骤和完成后的检查点，恢复后从连接验证继续，不重复安装。

## 配置客户端：Codex 示例

以下依据 [OpenAI 官方 MCP 配置文档](https://learn.chatgpt.com/docs/extend/mcp)。实施时核对当前客户端版本及有效配置；其他客户端使用各自实际配置格式。

Codex 默认用户配置为 `~/.codex/config.toml`，Windows 通常为 `%USERPROFILE%\.codex\config.toml`；也支持受信任工程中的 `.codex/config.toml`。存在自定义配置目录或项目覆盖时先查清有效配置来源。只读取相关服务器条目，不输出整个配置文件中的秘密。

在配置前备份将修改的文件。已存在同名条目时合并，保留无关服务及原有有效选项；不要重复添加同名 TOML 表。只需要指导时提供拟合并片段，不实际写入配置。

### Streamable HTTP

服务说明确认使用 Streamable HTTP 时，配置 `url`。本机曾使用的下面地址仅为示例，端口和路径必须替换为本次服务的真实值；`ugcaskq` 是此处的服务名称，不能据此假定所有安装的工具名和地址相同。

```toml
[mcp_servers.ugcaskq]
url = "http://127.0.0.1:12463/mcp"
enabled = true
```

如需要认证，按服务说明使用客户端支持的凭据方式；文档与报告不写入真实密钥。不要把普通 HTTP GET 成功、404 或 405 单独当作 MCP 的成功或失败结论，应使用符合该传输协议的握手与工具请求。

### STDIO

只有服务说明明确提供 STDIO 启动入口时才使用下面形式。示例路径不是可运行的安装命令，必须换成已核实的可执行文件、参数及工作目录。

```toml
[mcp_servers.editor_mcp]
command = "C:/MCP-Service/server.exe"
args = []
cwd = "C:/MCP-Service"
enabled = true
```

HTTP 服务不能仅凭地址改写成 STDIO，反之亦然。若说明要求通过解释器启动脚本，则 `command`、`args` 按真实解释器及脚本填写。

### 使配置生效

保存后通过客户端提供的 MCP 重新连接或重新加载入口加载配置；需要重启时只重启对应客户端。CLI 可用时，`codex mcp list` 用于核对配置，TUI 的 `/mcp` 用于查看活动服务；两者都不能替代下面的工程读取验证。工具仍不可见时，检查启用状态、工具过滤和客户端加载错误，再按客户端支持方式刷新会话。

## 连接与能力验收

按依赖顺序验证，每一步记录实际结果；失败后停止后续依赖检查，但可继续独立的本地只读预检。

1. **发现工具。** 从本次会话发现编辑器相关工具，阅读其描述和参数。此服务通常提供 `ue_read`、`ue_py`、`ue_pie`，实际名称以服务为准。工具未暴露时先处理客户端加载，不凭记忆调用不存在的工具。
2. **请求工程上下文。** 使用发现的读取工具请求 `ctx:`，记录目标工程目录、工程名、挂载根和 PIE 状态，与本次明确目标及 `.ugcproj` 核对。只拿到 MCP 初始化响应或工具列表不算工程连通。
3. **核对必需能力。** 通过工具说明、API 发现及只读查询，确认目标资产读取、蓝图/组件编辑与编译保存、结构体与表操作、Python 执行、PIE 控制及日志读取的支持情况。预检不创建资产、不试写、不启动或停止 PIE；写入与启动是否真正成功留给确认后的部署验收。读权限不足或功能缺失时列明，不宣称部署能力齐备。
4. **有限时重试。** 使用客户端支持的请求超时；自建诊断请求需设置明确超时，例如握手 10 秒、上下文读取 30 秒。相同失败在无状态变化时最多重试一次，保留错误摘要；恢复连接、切换工程或重启后再验证，避免反复挂起请求或重装。
5. **返回预检。** 分别报告安装、配置加载、服务可达、工程连通和能力核对结果。任何必需项未就绪，保留接续位置；就绪后刷新完整报告，进入 SKILL.md 原有部署确认。

如果当前客户端不暴露 MCP 工具，但维护方提供另一种受支持的调用入口，可核对协议和能力后使用；不能默认把旧工程的固定地址脚本当成通用替代，也不能绕过服务的写入约束。无可验证入口时明确报告未就绪。

## 报告需包含的证据

- 编辑器版本、服务来源及版本（未取得时明确写未知）、客户端配置来源和所用传输类型。
- 配置是否加载、只读请求结果或错误摘要、实际工程与挂载根、PIE 状态及能力缺项。
- 已完成的环境准备动作、必要的用户手动步骤，以及下一次从哪里继续。
- 分别标注“MCP 已就绪”和“框架部署尚未开始/未完成/已完成”；只有框架自身部署与本次启动验收通过，才能报告完整部署成功。
